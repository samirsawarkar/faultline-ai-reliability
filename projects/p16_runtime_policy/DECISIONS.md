# Decisions for P16 Runtime Policy Enforcement

- **Boundary Enforcement Before Schema Validation**: Runtime policy intercepts tool calls directly after model generation and before Pydantic schema adaptation (`TOOL_CALL_ADAPTER.validate_python`). If a hostile model generates unknown tool names (`execute_shell`) or arbitrary payloads, evaluating before the schema adapter prevents unhandled serialization crashes and returns a typed denial observation cleanly to the agent loop.
- **Architectural Authorization vs. Prompt Detection**: Prompt injection and jailbreak detectors rely on heuristic text scoring that inevitably degrades under novel attacks. Placing deterministic authorization at the tool interface ensures that even if an attacker gains full control over the model's weights and generation, the agent cannot execute unauthorized operations.
- **High-Volume False-Positive Measurement ($n=2,000$)**: A guardrail with an unmeasured false-positive rate is unshippable. Rather than evaluating a trivial dozen calls, we evaluated 2,000 legitimate tool calls from the standard-pool scenario suite against the solver stub. Measuring zero false positives across 2,000 calls bounds the false-positive rate within $[0.00\%, 0.18\%]$ at 95% Wilson confidence.
- **Typed `PolicyProtocol` Boundary**: Rather than typing the policy hook as `Optional[Any]`, we defined a `@runtime_checkable` `PolicyProtocol` defining the `evaluate(raw_call, run_id, trace_store)` signature. This enforces static and runtime verification across architectural boundaries.
- **Explicit Scope Boundaries**: We explicitly delineate the scope of runtime policy: it is strictly execution authorization against a compromised model. It does not attempt prompt classification (P9) or tool poisoning defense (P8).
